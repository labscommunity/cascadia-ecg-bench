Follow-up round (same day): memory window, concurrency, device mix, 122B fix

The iGPU memory window on 32 GB boxes can be raised, and it changes everything

The real limit is a dxgkrnl setting Intel's INF installs at 57% (GraphicsDrivers\MemoryManager\SystemPartitionCommitLimitPercentage); at 85% the per-process GPU budget goes from 17.2 to 26.1 GiB. The whole 35B on one NUC goes from 1.7–1.9 to 33 (steady 30) tok/s, and the 122B runs all-local on three NUCs at 2.9–3.3 tok/s.

OVMS continuous batching scales linearly to 8 streams

On the 64 GB box: 32 tok/s for one stream, 132 tok/s combined at 8 streams (16.6 each), at 34–36 W throughout, so 3x the tokens per joule of single-stream serving.

CPU decode is a loss, the NPU does not load

Dense Qwen3-8B on one 32 GB box: 22 tok/s on the GPU, 11 on the CPU, with 1k-token prefill at 0.3 s vs 22 s. Neither the 8B nor the 0.6B compiles on the NPU with OpenVINO 2026.4.1 (driver compiler error); the NUCs have no NPU driver. A phase split (NPU prefill, GPU decode) does not exist in these engines.

The 122B GPU failure is fixed in the builder

GPTQ experts are symmetric (every zero point is 8) and the GPU MoE fusion rejects that form. Emitting signed INT4 experts without a zero point (--expert-sym, bit-identical values) compiles. The rebuilt 35B runs whole on the 64 GB GPU 9% faster than Intel's export at equal accuracy (A6).

The 122B runs on the NUCs now, but three 32 GB boxes thrash

With the fixed IR the 3-stage 122B loads and answers on alpha + beta + charlie (health in 14 s), at 0.57 tok/s: each 20–23 GB stage exceeds the 18.4 GB the driver keeps resident per iGPU, so every rank pages weights on every token. Stages must stay under ~18 GB: four or more 32 GB nodes, or a 64 GB tail.

With four stages that fit, the 122B runs cleanly, and the relay sets the speed

alpha + beta + charlie + the 64 GB Tiber box as tail: no paging (head copy engine 3%), 2.0 s TTFT on a short prompt, 1.2–2.7 tok/s decode at every prompt length because each token crosses the Tiber relay twice. GSM8K-20: 17/20 (3 misses = 400-token truncations; 35B: 18–19/20 on the same questions). A fourth local 32 GB node would make it LAN-bound (est. 5–8 tok/s).

Memory window on 32 GB Panther Lake: the real knob

Two settings look alike. Intel's GMM\GpuSystemMemoryPinninglimit (what the first attempt changed) only moves the total that OpenVINO reports (16.5 → 24.8 GiB). The segment the Windows video memory manager actually enforces, and the per-process budget it derives from it, come from HKLM\SYSTEM\CurrentControlSet\Control\GraphicsDrivers\MemoryManager\SystemPartitionCommitLimitPercentage, which Intel's INF sets to 57 ("DXGK regkey to override the default 50% pinning limit to 57%") and which Intel Graphics Software's "Shared GPU Memory Override" slider writes together with the GMM key. The budget, read with D3DKMTQueryVideoMemoryInfo (the number Task Manager shows), is the resident cap seen in every thrashing run of this report.

Measured on delta (Panther Lake, 32 GB, the only box with an NPU driver) with dense INT4 exports that fit every device; quick protocol, two runs each; decode is the end-to-end rate of the second, prefix-cached request. The CPU has the same DRAM bandwidth as the iGPU but far less compute, so it loses 2x on decode and 55–75x on prefill; for the 35B the CPU plugin's 2x weight residency makes it worse still. The engines run prefill and decode on one device: the NPU pipeline as two static sub-models on the NPU, the GPU pipeline on the GPU; there is no cross-device KV hand-off. Cascadia's pipeline engine splits by layers, so the available "mixed" layouts are a GPU head rank feeding a CPU tail rank and OpenVINO's HETERO:GPU,CPU; both are in the last rows.

The mixed pipeline answers "CPU for decode" directly: with half of the 35B's layers on a CPU rank, decode halves on a 1k-token prompt and falls 5x on a 7.7k-token prompt (the CPU stage's attention over a long KV cache dominates), prefill is 5–8x slower, the GPU head idles 94% of the time waiting for the tail, and the CPU rank needs twice its stage size in RAM. The CPU is a fallback for a box whose GPU window is full, not a decode device.

OpenVINO's heterogeneous plugin does not help either: with GPU first and CPU as fallback it places every supported layer on the GPU (the utilization profile is identical to plain GPU) and decodes the whole 35B at 1.3–1.4 tok/s on a 32 GB box, 20% slower than the plain-GPU oversubscribed run. It does not spill weights to the CPU to relieve the GPU window.

The GPU plugin compiles every 122B stage with the --expert-sym build (the fix at 122B scale), and the pipeline is healthy 14 s after launch. Decode is flat at 0.57 tok/s on every prompt length because all three ranks page weights through an 18.4 GB resident segment (the copy engine at 26% is the paging); the whole 35B on one NUC shows the same signature at 1.7–1.9 tok/s with a 1 GB overshoot, here it is 1.4–4.6 GB per rank. The run was cut after the first repeats; the task-accuracy pass moved to the 4-stage layout.

In the 4-stage layout every stage fits its GPU and the speed is set by the network alone: each token crosses the NUC-to-Tiber relay twice (activations out to the tail, the sampled token back to the head) at 110–350 ms a crossing, so decode is about 2 tok/s at every prompt length and the GPUs idle 95% of the time; the 7.7k-token prefill takes two minutes because 7.7k tokens of activations cross the relay at each hop. Head package power 3.1 W idle, 6.8 W decoding; chain total 28.7 W (alpha 7.6 + beta 8.3 + charlie 4.5 + tate-07 8.3), i.e. 0.07 tok/J: four GPUs mostly idling on the relay. What the run establishes is that the 122B IR is correct end to end, that four stages load and run inside their GPU segments, and that the LAN hops between the NUCs cost nothing visible. By the 35B chain's scaling (18 tok/s on 3 NUCs with 3B active parameters, 3.3x fewer than the 122B's 10B), a 4-NUC all-local 122B would land at roughly 5–8 tok/s: an estimate, not a measurement.
